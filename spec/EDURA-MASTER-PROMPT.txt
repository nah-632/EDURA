1. ROLE
Act as an integrated team in one: Product Architect, UX/UI Designer, Full-Stack Engineer, Database Architect, Security Engineer, QA Engineer, DevOps Engineer. You own the full lifecycle of this build.
2. PROJECT CONCEPT
Edura connects students/parents in Bahrain with qualified private tutors — with special focus on graduates of teacher-training/education colleges and other qualified individuals seeking teaching opportunities. Covers Primary, Intermediate/Preparatory, and Secondary/High school.
Core discovery-to-booking flow: browse/search tutors → review qualifications and profile → select subject, lesson type, teaching method, date/time → submit booking request.
Payment workflow (v1, manual):
booking created → customer handed off to WhatsApp with a dynamically generated message → instructed to pay via BenefitPay → customer sends payment proof via WhatsApp → admin manually verifies → admin confirms booking → tutor and customer notified.
Do NOT implement an online payment gateway in v1. The architecture MUST allow one to be added later without rebuilding the booking system (see §14).
3. CORE BUSINESS MODEL
	•	Tutors may pay a subscription fee (monthly/annual) to stay active. Support: subscription status, active/inactive, expiry, grace period, admin-controlled pricing (never hard-coded).
	•	Architecture must also support a future per-booking platform commission, without a rebuild.

5. BRAND / DESIGN DIRECTION
Premium, modern, trustworthy Bahraini education platform. Communicate: trust, education, professionalism, safety, human connection, modern technology, local Bahraini identity, premium quality without feeling corporate or cold. Avoid generic "school website" design — this should feel like a modern tech marketplace fused with a premium education brand.
Use excellent typography, strong hierarchy, elegant cards, professional tutor profile cards, subtle purposeful animation, generous whitespace, high-quality icons, responsive layouts, accessible contrast, mobile-first design. Motion improves UX — it never distracts.
6. LANGUAGES
Arabic (primary, RTL) and English (LTR), fully implemented from the start — not a handful of translated labels. Every buttons, form, validation message, nav item, dashboard, email, notification, booking detail, admin screen, empty state, and error state must exist in both languages, switchable throughout the entire app. Use professional Arabic typography (Cairo, per §4) — never a low-quality Arabic font fallback.
7. ROLES
7.1 Student / Parent
Create account, login, browse/search/filter tutors, view tutor profile, select subject/stage/lesson type/method/date-time, submit booking, view booking history/status, receive notifications, contact platform via WhatsApp, rate tutor after a completed lesson, manage profile. Support parent-books-for-child: parent name, student name, student grade/stage, student age (optional), student gender (where operationally relevant), subject, notes.
Minor-data rule: student records tied to a minor are a distinct sensitive data category — access-controlled separately from the parent account's own PII, never exposed on public tutor-facing views, and covered explicitly in the privacy policy (§44).
7.2 Tutor
Dedicated dashboard. Registration collects: full name, profile photo, phone, email, city/area, nationality (if required), qualification, university/college, major, graduation year, subjects taught, stages, years of experience, short bio, teaching method, home/online availability, preferred areas, price per lesson/hour, available days/times, supporting documents.
Profile is never publicly visible by default. Initial status: PENDING VERIFICATION. Statuses: Pending, Under Review, Approved, Rejected, Suspended, Expired Subscription. Only APPROVED + ACTIVE tutors appear publicly.
8. TUTOR PROFILE PAGE
Display: photo, name, verification badge, qualification, specialization, subjects, stages, areas served, teaching methods, experience, rating, completed-lessons count, bio, availability, price, home/online flags, languages spoken, reviews.
Primary CTA: "احجز حصة". Secondary CTA: "تواصل معنا".
Never publicly expose: private email, private address, internal documents, identity documents, payment information.
9. TUTOR SEARCH
Filter by subject, stage, city/area, lesson type, home/online, price range, gender (if the business enables it), rating, availability, experience, qualification. Tutor cards show: name, qualification, subject, area, rating, price, teaching options, verification status, book button.
10. LESSON TYPES (admin-configurable, not hard-coded)
Private Lesson, Intensive Course, Exam Preparation, Subject Revision, Small Group (architecture-ready for multiple students later).
11. TEACHING METHODS
Home (tutor visits student) and Online (Zoom). Store Zoom links manually per booking for now — no fake video system. Architecture must allow a future meeting-provider integration (see §14).
12. BOOKING FLOW
	1.	Select tutor.
	2.	Select student, subject, stage, lesson type, method, date, time, duration, location (if home), notes.
	3.	System calculates/displays price.
	4.	Customer confirms request.
	5.	System creates a unique booking ID, format EDU-DDMMYYYY-XXXX (e.g. EDU-26092026-0001).
	6.	Status → PENDING_PAYMENT.
	7.	Show a professional confirmation page.
	8.	Generate a dynamic WhatsApp message (never static/generic) containing: booking ID, customer name, student name, tutor, subject, stage, lesson type, method, date, time, duration, price, area (if applicable), notes.
	9.	Open WhatsApp to the official number: +973 6666 1238.
Concurrency requirement: booking creation must be transaction-safe at the database level (not just validated in application code) so two simultaneous requests for the same tutor/date/time cannot both succeed. Use a DB-level unique constraint or row-level locking on the (tutor, date, time-range) tuple — state explicitly which mechanism you used and why.
13. WHATSAPP + BENEFITPAY MANUAL PAYMENT WORKFLOW
Payment method shown to customer: BenefitPay, with instruction copy: "Please complete the payment through BenefitPay and send the payment confirmation/proof through WhatsApp." Admin verifies manually.
Booking status state machine (enforce transitions server-side, no arbitrary status jumps): Pending Payment → Payment Verification → Paid → Confirmed → Tutor Accepted → Scheduled → In Progress → Completed | Cancelled | Rejected | Refund Requested → Refunded.
14. FUTURE-READY PROVIDER ABSTRACTIONS
Design these as swappable interfaces so v1's manual implementation never blocks a future integration without rewriting core business logic:
	•	PaymentProvider → v1: ManualBenefitPayProvider. Future: online gateway.
	•	NotificationProvider, EmailProvider, WhatsAppProvider, VideoMeetingProvider, StorageProvider — same pattern: simple v1 implementation behind an interface the booking/subscription logic depends on, not the concrete provider.
15. ADMIN DASHBOARD
Manage: tutors (view/approve/reject/suspend/reactivate/edit/verify/view documents/view subscription), students-parents (view/edit/suspend/reactivate/view bookings), bookings (view/filter/search/detail/status change/payment verification/confirm/cancel/reassign), payments (records/status/mark-verified/reference/verification date/verifier/manual refunds), subjects/stages/areas/lesson-types (full CRUD), pricing (tutor subscription, lesson fees if platform-priced, future commission, optional service fees — never hard-coded), reviews (moderate/hide/restore/report), notifications (announcements, booking/tutor/student notifications), CMS (homepage sections, FAQ, About, contact info, Terms, Privacy, hero text, promo banners).
Admin account hardening (mandatory, not optional): strong password policy enforced server-side, and either MFA or an equivalent step-up verification for admin login — the admin account is the highest-value target in this system given tutor documents and payment records.
16. ADMIN ANALYTICS
Total/active/pending/suspended tutors, total/active students, total/pending/confirmed/completed/cancelled bookings, pending/verified payments, subscription revenue, booking revenue, monthly revenue, recent bookings. Charts only where they genuinely aid understanding. Never fabricate analytics data — if there's no data yet, show a real empty state.
17. NOTIFICATIONS
New booking, payment pending/verified, booking confirmed/cancelled, tutor approval/rejection, subscription expiring, lesson reminder, review request. Architecture ready for future Email/WhatsApp-API/SMS/Push — never claim one of these channels is live unless it's actually wired up.
18. BOOKING REMINDERS
Scheduled-job-ready: 24h-before and 2h-before lesson reminders, post-lesson review request.
19. REVIEWS
Only after a completed booking. Fields: rating (1–5), written review, optional categories. Block: duplicate reviews per booking, reviews on cancelled bookings, reviews before completion. Admin moderation required.
20. SECURITY (first-class requirement, not a checklist to skim)
Secure auth, password hashing, RBAC, server-side authorization on every sensitive action (never trust frontend permission checks), input validation, output sanitization, rate limiting — explicitly and non-optionally on login and booking-creation endpoints, CSRF protection where applicable, secure session handling, secure DB rules, file upload restrictions (type + size + storage location), no sensitive data in client-side code, no exposed API secrets, environment variables for all secrets, protected admin routes, audit logging.
21. DOCUMENT VERIFICATION (tutor documents)
Never expose public URLs to tutor documents. Store behind access control; only authorized admins can retrieve them, via time-limited signed URLs, not permanent public links. Log every access (who, when, which document) in the audit log.
22. DATABASE
Normalized schema, minimum entities: users, profiles, tutors, students, subjects, educational_stages, areas, lesson_types, tutor_subjects, tutor_stages, tutor_availability, tutor_documents, subscriptions, subscription_plans, bookings, booking_items, payments, payment_proofs, reviews, notifications, messages, settings, audit_logs. Foreign keys, indexes, timestamps, soft deletion where appropriate — no god-tables.
23. DATABASE DESIGN PRINCIPLES
UUIDs where appropriate, created_at/updated_at, status fields, FKs, unique constraints, indexes, transaction-safe booking creation (per §12). Tutor availability checked server-side — never trust the frontend calendar alone.
24. BOOKING CONFLICT PREVENTION
A tutor cannot receive two confirmed bookings for overlapping date/time. Only statuses representing an active reservation block a slot; cancelled/rejected bookings never block availability. Enforce server-side per §12.
25. DATA RETENTION & ACCOUNT DELETION
Define and implement a data retention policy: how long booking/payment/document records are kept, and a working "delete my account" path for students/parents that removes or anonymizes personal data while preserving what's legally/financially required to keep (e.g. payment audit trail) — flagged clearly which is which.
